# DECISIONS — 架构与产品决策记录

> 每条采用：编号 / 状态 / 决策 / 理由 / 影响 / 重新评估条件。状态：`Accepted` 已确认，`Proposed` 待验证。改动既有决定需要新增 ADR，不覆盖历史。

## ADR-001 — 单人本地使用

- 状态：Accepted
- 决策：不引入用户账户、多租户、社交与课程商业化功能。
- 理由：只给自己使用，降低维护成本。
- 影响：API 和页面默认一个使用者，但仍需保护本地上传和 API Key。

## ADR-002 — 用户自行在本地运行代码

- 状态：Accepted
- 决策：网页仅允许手动上传代码和日志，不实现在线 IDE、服务器执行或强制 CLI。
- 理由：不增加日常操作负担，兼容个人 IDE、GPU 和各类实验环境。
- 影响：评审为静态分析+日志辅助，不得宣称独立执行或验证。

## ADR-003 — Project 为核心组织单位

- 状态：Accepted
- 决策：Project 组织课程、资料、会话、提交和计划；基础知识可跨项目复用。
- 理由：同时学习不同领域且保持上下文边界。

## ADR-004 — 固定课程与自由学习共存

- 状态：Accepted
- 决策：固定路线保留核心目标；自由问答/论文导入按需增加临时内容。
- 理由：保证系统性与灵活性。

## ADR-005 — 自动知识沉淀、核心内容审核

- 状态：Accepted
- 决策：一般笔记自动生成草稿；核心公式、标准解法、评测规则及覆盖已确认内容须审核。
- 理由：降低操作负担，同时避免 AI 错误污染知识库。

## ADR-006 — 跨项目修改必须确认

- 状态：Accepted
- 决策：Agent 可主动生成建议，但不能未经确认更改其他项目的学习计划。
- 理由：保持其他项目学习节奏和用户控制权。

## ADR-007 — 一个主 Agent

- 状态：Accepted
- 决策：一个主 Teaching Agent 协调既有教学和明确的工具/服务，不引入多 Agent 团队。
- 理由：避免不必要的复杂度和调试成本。

## ADR-008 — 先 Fork 并保留 StudyForge 主技术栈

- 状态：Accepted（以本地基线验证为前提）
- 决策：优先复用 Next.js/React、FastAPI、SQLite 和课程/FSRS/Tutor，不先改成 Vue。
- 理由：减少重写和复用已存在功能。
- 重新评估条件：P0 测试表明上游功能不可稳定运行或维护成本明显过高。

## ADR-009 — Markdown + SQLite + 本地文件

- 状态：Accepted
- 决策：知识正文可维护为 Markdown；SQLite 管理关系和状态，原始资料保留在本地文件系统。
- 理由：易阅读、备份、扩展；暂不需要向量/图数据库。

## ADR-010 — 使用正式迁移机制

- 状态：Proposed
- 决策：涉及复杂表关系时采用 Alembic，保留 SQLite 升级与回滚测试；简单全新表可先安全增加。
- 理由：上游自定义迁移仅适合简单新增列。
- 确认条件：P1 开始前通过实际旧数据迁移演练。

## ADR-011 — 代码评审证据分级

- 状态：Accepted
- 决策：输出分别标记 confirmed_static、user_reported、inferred、needs_local_check。
- 理由：AI 没有执行上传代码，必须诚实表达证据强度。

## ADR-012 — 模型与文档来源可替换

- 状态：Proposed
- 决策：先复用 Anthropic/Ollama/Fake Provider，其他 API 在实际需要时适配；来源资料以可追溯片段组织。
- 理由：避免初期无限扩展模型兼容工作。

## ADR-016 — P1 项目新增表与关联事务
- 日期：2026-10-20
- 状态：Accepted（旧库升级、重复启动及共享历史测试通过）
- 决策：Project/ProjectCourse 为独立新表，沿用 init_db/create_all；不修改旧课程字段或重建表。现有复杂迁移边界不扩展，未来涉及旧表结构变更再引入正式工具。
- 理由：本次仅安全新增两张表，历史库与新库结构一致已实测，无需额外迁移依赖。
- 影响：归档只更新项目状态；条件 UPDATE 先获得 SQLite 写锁，再修改关联，避免归档竞态。SQLite 外键关闭时通过 ORM 双向清理 membership，生产课程删除入口先取得写锁。升级前快照，回滚旧代码可忽略新增表；需要数据级恢复时遵循 OPERATIONS 的备份恢复步骤，不提供破坏性删表命令。

## ADR-015 — 用户指定的 Gemini 兼容网关
- 日期：2026-10-20
- 状态：Accepted（用户授权使用已有 .env 验证）
- 决策：新增基于已有 httpx 的 Chat Completions adapter，支持 gemini/openai；读取 LLM_*，保留旧 STUDYFORGE_* 优先级，未知 provider 明确拒绝。
- 理由：根配置使用 Gemini 网关，原上游 adapter 无法读取。协议参考 Google 官方 OpenAI compatibility 文档：<https://ai.google.dev/gemini-api/docs/openai>。
- 影响：TLS 验证、不跟随重定向、不回显响应或密钥；拒绝截断/空答案，保留失败 token 使用；仍走 MeteredLLM。未知模型费用采用已有 fallback 并标记 approximate，不当作真实账单。

## ADR-013 — 本机开发与按风险验证
- 日期：2026-10-20
- 状态：Accepted（用户明确要求）
- 决策：默认本机 uv/Python + Node/Next，不使用 Docker 进行日常启动与测试；Compose 仅保留为可选工具。优先完成功能，每项运行最小必要验证，在集成节点执行质量门禁，减少重复全量测试。
- 理由：容器首次构建/下载过慢，用户主要在本机使用。
- 影响：保留已获得的容器测试证据但不与本机结果混称；禁止执行用户上传代码的产品边界保持适用。

## ADR-014 — 界面与教学双语
- 日期：2026-10-20
- 状态：Accepted（用户明确要求）
- 决策：默认简体中文，允许切换 English，持久保存同一选择供 SSR、客户端和后续 AI 教学请求使用。已存学习内容与上传来源保留原文。
- 理由：中英文使用需求并存，避免改变现有答题答案和 concept key。


## ADR-017 — 取消时间驱动机制，转向纯知识掌握驱动
- 日期：2026-10-20
- 状态：Accepted（用户明确指令）
- 背景：原 StudyForge 具备考试倒计时（Deadline）、可用天数（Days Off）、日历导出（ICS）及按日期的到期复习安排。
- 决策：
  1. 完全取消时间驱动功能：移除 Planning、Deadline、Days Off、Calendar 导出等产品功能；取消 56 天等固定周期的表述。
  2. 确立纯知识驱动闭环：选择项目 → 选择知识点 → 学习 → 本地代码实践 → 上传结果 → AI 静态检验 → 错因分析 → 补充练习 → 更新掌握状态。
  3. FSRS 底层实现与历史日志完整保留，但不按到期日期强制推送复习；复习由用户自主发起，或由 Agent 根据知识漏洞与错题推荐。
  4. 绝不删除或损坏已有的学习历史、答题记录与复习日志。
- 影响：前端导航与课程详情页精简（移除 Plan 标签、DeadlineForm、DaysOff 等）；后端保留底层数据表兼容，规划类接口降级或逐步下线。
