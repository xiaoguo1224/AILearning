# DECISIONS — 架构与产品决策记录

> 每条采用：编号 / 状态 / 决策 / 理由 / 影响 / 重新评估条件。状态：`Accepted` 已确认，`Proposed` 待验证。改动既有决定需要新增 ADR，不覆盖历史。

## ADR-001 — 单人本地使用

- 状态：Accepted
- 决策：不引入用户账户、多租户、社交与课程商业化功能。
- 理由：只给自己使用，降低维护成本。
- 影响：API 和页面默认一个使用者，但仍需保护本地上传和 API Key。

## ADR-002 — 用户自行在本地运行代码

- 状态：Accepted
- 决策：网页仅允许手动上传代码和日志，不实现在线 IDE、服务器执行或强制 CLI。
- 理由：不增加日常操作负担，兼容个人 IDE、GPU 和各类实验环境。
- 影响：评审为静态分析+日志辅助，不得宣称独立执行或验证。

## ADR-003 — Project 为核心组织单位

- 状态：Accepted
- 决策：Project 组织课程、资料、会话、提交和计划；基础知识可跨项目复用。
- 理由：同时学习不同领域且保持上下文边界。

## ADR-004 — 固定课程与自由学习共存

- 状态：Accepted
- 决策：固定路线保留核心目标；自由问答/论文导入按需增加临时内容。
- 理由：保证系统性与灵活性。

## ADR-005 — 自动知识沉淀、核心内容审核

- 状态：Accepted
- 决策：一般笔记自动生成草稿；核心公式、标准解法、评测规则及覆盖已确认内容须审核。
- 理由：降低操作负担，同时避免 AI 错误污染知识库。

## ADR-006 — 跨项目修改必须确认

- 状态：Accepted
- 决策：Agent 可主动生成建议，但不能未经确认更改其他项目的学习计划。
- 理由：保持其他项目学习节奏和用户控制权。

## ADR-007 — 一个主 Agent

- 状态：Accepted
- 决策：一个主 Teaching Agent 协调既有教学和明确的工具/服务，不引入多 Agent 团队。
- 理由：避免不必要的复杂度和调试成本。

## ADR-008 — 先 Fork 并保留 StudyForge 主技术栈

- 状态：Accepted（以本地基线验证为前提）
- 决策：优先复用 Next.js/React、FastAPI、SQLite 和课程/FSRS/Tutor，不先改成 Vue。
- 理由：减少重写和复用已存在功能。
- 重新评估条件：P0 测试表明上游功能不可稳定运行或维护成本明显过高。

## ADR-009 — Markdown + SQLite + 本地文件

- 状态：Accepted
- 决策：知识正文可维护为 Markdown；SQLite 管理关系和状态，原始资料保留在本地文件系统。
- 理由：易阅读、备份、扩展；暂不需要向量/图数据库。

## ADR-010 — 使用正式迁移机制

- 状态：Proposed
- 决策：涉及复杂表关系时采用 Alembic，保留 SQLite 升级与回滚测试；简单全新表可先安全增加。
- 理由：上游自定义迁移仅适合简单新增列。
- 确认条件：P1 开始前通过实际旧数据迁移演练。

## ADR-011 — 代码评审证据分级

- 状态：Accepted
- 决策：输出分别标记 confirmed_static、user_reported、inferred、needs_local_check。
- 理由：AI 没有执行上传代码，必须诚实表达证据强度。

## ADR-012 — 模型与文档来源可替换

- 状态：Proposed

## ADR-017 — 取消时间驱动机制，转向纯知识掌握驱动
- 日期：2026-10-20
- 状态：Accepted（用户明确指令）
- 背景：原 StudyForge 具备考试倒计时（Deadline）、可用天数（Days Off）、日历导出（ICS）及按日期的到期复习安排。
- 决策：
  1. 完全取消时间驱动功能：移除 Planning、Deadline、Days Off、Calendar 导出等产品功能；取消 56 天等固定周期的表述。
  2. 确立纯知识驱动闭环：选择项目 → 选择知识点 → 学习 → 本地代码实践 → 上传结果 → AI 静态检验 → 错因分析 → 补充练习 → 更新掌握状态。
  3. FSRS 底层实现与历史日志完整保留，但不按到期日期强制推送复习；复习由用户自主发起，或由 Agent 根据知识漏洞与错题推荐。
  4. 绝不删除或损坏已有的学习历史、答题记录与复习日志。
- 影响：前端导航与课程详情页精简（移除 Plan 标签、DeadlineForm、DaysOff 等）；后端保留底层数据表兼容，规划类接口降级或逐步下线。


## ADR-019 — 自由学习的检索、引文与练习边界
- 日期：2026-10-21
- 状态：Accepted（P3 定向与全量后端回归、前端 tsc/lint/test/build 通过）
- 决策：
  1. 会话（AgentSession）严格属于一个项目。检索只在该项目的 `resource_chunks` 内进行：先 FTS5，无命中时用有界的 LIKE 回退（覆盖 FTS5 分词漏掉的中文短语与带标点的提问）。跨项目检索会让“引文指向本项目资料”这句承诺静默失效，因此不做。
  2. 引文以标记（S1..Sn）给出，模型只能引用本次实际提供过的标记；未提供过的标记在落库前丢弃，不进入 `source_refs`。`source_refs` 是快照（文件名、定位、chunk id），不是外键：资料之后被删除，也不该把“有出处的断言”变成“无出处的断言”。
  3. 引用块不可被引用内容闭合：只改写精确的 `</SOURCES>`、`</CONVERSATION>`、`</QUESTION>` 令牌，不做全角括号替换，保证源码里的 `a < b` 原样保留。
  4. 模型调用失败或输出不可解析时不落库：问题不会留下一个没有回答的空壳，重试不会产生重复提问。
  5. 教学策略只有一个所有者：`app/teaching.py` 持有“先解释再提问”“两个回答字段”“四种情形”“共同拒绝项”“围栏段落”，Tutor 与自由学习共用；各端只保留自己成立的规则（Tutor 的调度器拒绝、guided 模式；自由学习的引文与不执行代码）。Tutor 的 system prompt 在抽取前后逐字节一致。
  6. 由提问生成的“临时讲解 + 练习”中，讲解作为助手消息入库（与回答同源的引文快照），练习进入 `variant_exercises` 并以 `draft` 保存，可通过既有提交入口 `variant_id` 关联；会话 id 与原始提问只作追溯，不设外键、不级联删除。
- 理由：引文正确性是这个功能的全部价值；证据边界（哪些是资料说的、哪些是模型知道的、哪些没被验证）必须由 schema 与界面共同承载，而不是靠提示词自律。
- 影响：单个问题的上下文有上限（5 段 / 6000 字符 / 6 轮历史），超长资料不会被完整送入；练习未经人工审核，界面必须标明“草稿、未运行”，不出现“已验证”表述。
- 重新评估条件：需要跨项目引用，或需要把自由学习结论沉淀为知识条目时（P4-01/02），另立决策，不在检索层放宽。

## ADR-018 — 提交与评审的存储与证据边界
- 日期：2026-10-20
- 状态：Accepted（P2 定向测试与全量后端回归通过）
- 决策：
  1. `SubmissionArtifact` 的文本内容存入 SQLite（代码 512KB、日志 2MB 上限），不落独立文件；备份一份数据库即完整备份提交记录。
  2. 上传文件与粘贴文本走同一套校验：扩展名白名单、大小上限、UTF-8 严格解码、拒绝二进制与含路径的文件名；只解码与静态解析，没有任何执行路径。
  3. 评审证据固定四类：`confirmed_static`（源码可证）、`user_reported`（用户日志声称）、`inferred`（静态与日志的相关性推断）、`needs_local_check`（需本地验证）。无日志时必给一条 `needs_local_check`，不把“未检查”写成“没问题”。
  4. 模型评审默认关闭，按需开启；模型失败或输出不合契约时降级为静态评审，并以 `llm_status=unavailable` 如实标注，不静默冒充 AI 结果。
  5. 二、三级提示与参考解法必须单独请求；参考解法一律标注 `ai_generated_unverified`。
  6. 变式题以 `draft` 保存，生成失败返回 502 而不是伪造题目；后续提交可通过 `variant_id` 关联草稿。
- 理由：整库备份最简单；避免在个人目录散落小文件与清理风险；证据分级与提示阶梯是产品硬约束，不能由响应体默认泄露。
- 影响：单个提交不适合承载超大文件（如完整训练日志 > 2MB），超出时提示用户裁剪；模型评审与变式题消耗额度，故均为显式动作。
- 重新评估条件：需要保留原始二进制附件，或单文件上限成为真实障碍时，引入独立资料目录与引用计数清理。

## ADR-020 — 知识草稿、审核版本与错因证据
- 日期：2026-10-21
- 状态：Accepted（P4-01/02/03 定向验收完成；P4-04 后端完成，前端待集成）
- 决策：知识正文和不可变版本统一存 SQLite；有引用的回答/讲解在会话事务内自动保存普通草稿，不再次调用模型，也不提升掌握等级。beyond 扩展不提升为有来源笔记。
- 去重：同标题复用已有条目，相似条目仅返回候选；任何自动化路径不覆盖已确认内容。
- 审核：核心定义/标准答案初始待审核，确认是独立操作；编辑确认稿退回待审核并追加版本。浏览器必须携带读取时的更新时间，409 时保留草稿，明确选择后才能丢弃本地编辑。旧调用方可继续使用无令牌接口，无法获得乐观并发保护。
- 错因：手工诊断不能标成已验证答题或提交证据；专用错题端点核验所属课程和错误答案。错因队列只读 FSRS，Again 不关闭任务。日期只用于审计先后，不用于安排学习。
- 影响与限制：当前仅有知识页，错因/复习任务前端与提交证据专用端点未完成；跨项目建议必须等待 P4-05 用户确认流程，不从错因服务直接写其他项目。
- 验证：后端知识/错因/Agent 74 项、迁移 24 项通过；前端知识审核 10 项及 tsc/lint/build 通过，详见 PROGRESS。

## ADR-021 — 评审错因与项目主动复习
- 日期：2026-10-21
- 状态：Accepted（P4-04 定向后端 75 项、前端 14 项与类型/lint/build 通过）
- 决策：评审缺少标准化概念键，由用户选择知识点，不能把模型 category 当作已确认知识。证据从服务器已存 finding 快照取得，验证评审所属项目，拒绝客户端证据正文及只有待本地检查的提示。
- 主动复习：只按本项目开放错因和关联课程取题，不按 due 过滤，不创建卡片；没有现成题目和卡片时明确提供学习/本地实践路径。共用既有 ReviewSession、答题与自评接口，主动模式隐藏学习间隔。
- 证据边界：后续有效自评可以关闭此前复习建议，界面明确“不代表代码已修复”。不通过聊天或诊断修改掌握度/FSRS。忽略只处理最新一条错因，保留记录，仍有其他错因时任务继续存在。
- 限制：证据 detail 最多 4000 字符，超长 finding 快照可能截断，不能承诺完整原文（完整评审仍存 CodeReview）。已打开页面仍沿用全局课程复习接口，归档只阻止新增诊断与项目新入口；共享概念的个人复习历史继续保留。旧全局 Today/Review 的日期驱动展示在 P5 集中处理。

## ADR-022 — 跨项目建议的确认与事务边界
- 日期：2026-10-21
- 状态：Accepted（P4-05/06 定向验证通过）
- 决策：由用户从开放错因选择目标项目，保存 pending 建议及不可变证据快照；创建和拒绝不写目标项目。只有 accepted 决定才在目标创建知识驱动复习任务，不改课程顺序或 FSRS，不设置日期。
- 一致性：同一错因/目标有唯一约束；SQLite 写锁后刷新决定状态，同决定重试幂等、相反决定 409。目标任务和建议接受状态一同提交，插入后失败整体回滚。
- 追溯：保留来源错因/项目、概念、证据、决定时间及目标任务 ID。逐条判断来源错因是否已复习或忽略，不因新出现同概念错误而复活旧证据。
- 归档：来源或目标归档均阻止接受；拒绝仍可处理建议。无需删除任何历史。现有核心内容和其他项目安排在用户接受前保持不变。
- 边界：当前目标由用户选择，未添加自动目标匹配或额外模型调用；创建建议和接受建议是两个明确操作。证据最长 4000 字符，目标任务表示确认的复习需要，不表示目标项目实测失败。

## ADR-023 — 只读课程知识树与练习进阶建议
- 日期：2026-10-21
- 状态：Accepted（P5-01 后端 6 项、前端 14 项及类型/lint/build 通过）
- 决策：知识树派生既有课程、课时、概念及项目知识关联，不新建重复历史实体。教材别名只映射阅读，不合并原始概念键；章节顺序不是前置关系。前置知识来自显式关联及人工配置的教学建议，所有节点可自由打开。
- 证据：只取项目课程内每题首次 lesson_quiz 和 review_session 作答，排除重试与 remedial_practice。最近三条正确、跨至少两题才建议进阶；开放错因或最近正式错答优先推荐复习。ready_for_advanced 不是 mastered，不写掌握、FSRS 或任何历史；时间流逝不自动降级。
- 教材：D2L 中文版白名单已核实 2.1 数据操作（含广播）、2.3 线性代数、2.5 自动微分、10.3 注意力评分函数、10.7 Transformer。未知主题不推测章节，视觉 Token/多模态/Radar/VLM 明确作为扩展路径，不声称完整内容已经创建。
- 交互：推荐基础/巩固/补先修/进阶/综合，准备提问时只建立空会话和可编辑草稿，用户发送才调用模型。原始资料与已存标题保留原文，应用文案双语。
- 限制：条目层无环关系合并概念后可能出现推荐环，目前仅展示建议且不锁课；未来自动排序前需检查投影环。只在错因记录、未进入课程/知识条目的概念仍在错因页查看，不声称本树覆盖全部诊断。

## ADR-024 — 内容审核只对确定的来源版本生效
- 日期：2026-10-21

## ADR-028 — 填空题从「简答 / 填空」里拆成独立题型
- 日期：2026-10-23
- 状态：Accepted
- 背景：`kind` 原本只有 `mcq / short / truefalse / code`，`short` 的标签是「简答 / 填空」，两种答案共用一个题型，也共用一套判分。填空的答案是一个词或数值，简答的答案是一段话，二者需要的判分方式相反。
- 决策：新增 `fill`，`short` 从此专指简答题。`QUIZ_KINDS` 扩为五种，`QuizGenerateInput.items` 的上限随之从 4 改为 `len(QUIZ_KINDS)`。前端题型清单收敛到 `frontend/src/lib/quizKinds.ts` 一处，替换原先散在三个组件里的本地常量。
- 存量数据**不迁移**：库里 8 道 `short` 题答案平均 146 字（7 道超过 40 字），本来就是句子作答，迁成 `fill` 会让精确匹配把每一道都判错。它们留在 `short` 下，正好由简答题的 AI 判分来判。若日后要迁，一条 `UPDATE quiz_items SET kind='fill' WHERE kind='short'` 即可，且可逆。
- 影响：新增题型要同时改 `QUIZ_KINDS`、`KIND_LABELS`、`_KIND_SPECS` 和 `zh-CN.json` 的 `quiz_kind_<kind>`；`quizgen.build_prompt` 的 kind 枚举改为由 `QUIZ_KINDS` 拼接，避免再出现"模型不知道有新题型"。

## ADR-029 — 判分策略按题型分派，两个答题端点合并到一处
- 日期：2026-10-23
- 状态：Accepted
- 背景：`/quiz/{id}/answer`（同步）与 `/quiz/{id}/answer/job`（后台，前端实际调用）判分口径不一致：前者对非 code 题走精确匹配，后者不看 kind 一律送模型，还把 `exact_ci` 写进 attempt 行。同一道题走哪条路，结论和记录都不同。
- 决策：新增 `main._judge_answer`，两个端点共用。策略表 `code_grade.GRADER_FOR_KIND`：`mcq / truefalse / fill` 精确匹配（`exact_ci`），`short / code` 由模型判（`llm_short` / `llm_code`）。`code_grade.grade_answer` 增加 `kind` 参数选择 system prompt，默认 `code` 以兼容既有调用。后台端点改用 `_record_attempt`，不再手写插入，从而获得重复提交保护、概念快照和正确的 grader。
- 理由：精确匹配对填空是准确的，对简答则把每一句改写都判错，与"用自己的话回答"的要求相反。
- 影响与风险：简答改由模型判分等于「意思对就过」，会顺着 `ever_correct` 影响掌握状态与进阶建议，属于产品语义变化而非纯技术改动。测试侧：所有"答题且用 `short` 题"的用例都改成 `fill`（它们不测判分策略），`FakeProvider` 新增判分分支，按 REFERENCE 与 SUBMITTED 精确比较给出 verdict，使离线测试行为与改动前一致且不产生真实调用。

## ADR-030 — 答案附件：内容寻址存储 + 字节嗅探
- 日期：2026-10-23
- 状态：Accepted
- 背景：简答题需要支持上传图片（手写答案拍照）、Word、Excel、PDF、代码/文本，并让模型据此判分。
- 决策：
  - 字节存 `backend/data/attachments/<sha256[:2]>/<sha256>`，DB 的 `attachments` 表只存元数据。文件名不参与路径，路径由内容哈希推导，目录穿越无从谈起；同一文件重复上传只存一份。
  - 类型由**字节嗅探**决定（PNG/JPEG/WEBP 魔数、`%PDF`、`PK\x03\x04` + 内部 `word/` 或 `xl/` 路径、UTF-8 可解码），不看扩展名也不看 Content-Type。
  - 拒绝带宏的 `.docm/.xlsm`（即使只读 XML 也拒绝），拒绝老格式 `.doc/.xls`（需外部转换器，与"单人本地、环境简单"冲突），单文件 10 MB、单次作答最多 5 个。
  - 文本抽取：PDF 用 `pypdf`（前 20 页），DOCX 复用 `resources/parser.parse_docx_chunks`，XLSX 用 `openpyxl`（新增依赖，纯 Python），文本/代码直接 UTF-8 解码。每附件 6000 字、合计 20000 字封顶，截断时在 prompt 里写明已截断。
  - 图片不转文字，作为多模态内容随请求发送；`LLMProvider.generate` 增加可选 `images`，`supports_vision` 由各 provider 声明（Ollama 按模型名判断）。模型不支持视觉且答案只有图片时返回 400 并提示，不给出"没看见也敢判"的结论。
- 影响：`attempts` 新增 `attachment_ids`（JSON），经 `ADDED_COLUMNS` 追加，老库自动补列，NULL 与 `[]` 同义。`MeteredLLM` 仅在有图片时传第四个参数，避免要求所有历史 provider 桩同步改签名。

## ADR-031 — 「题目解析」与「答案分析」是两个入口，不是同一个
- 日期：2026-10-23
- 状态：Accepted
- 背景：最初设想一个「AI 解析」按钮，未答题时讲题、已答题时讲错因。二者混在一起会让同一块内容承担两种意图。
- 决策：
  - **题目解析**沿用 `POST /quiz/{id}/solution`：prompt 只有题干、题型与标准答案，不含学习者作答，讲的是"这道题怎么解"，结果缓存到 `quiz_items.solution`。
  - **答案分析**新增 `POST /quiz/{id}/answer-analysis`（含 `/job`）：输入题干、参考答案、某次作答与判分结论，system prompt 明确"只评价这次作答，不要重讲题目"，输出「好在哪 / 问题出在哪 / 下次怎么答」。**不写入 `item.solution`**：一题多次作答的点评各不相同，写进去会让下一次作答看到上一次的点评。
  - 前端每题两个按钮；「答案分析」在 `attempt_state.attempts > 0` 时才出现，并在新一次提交后清空，避免旧点评被误读为新答案的点评。
- 影响：判分 feedback（一两句）与答案分析（多段）并存，深度不同不重复。答案分析目前不落库，刷新即失，属于有意取舍；若要保留历史，应在 `attempts` 加列而非复用 `solution`。

## ADR-032 — 存储一律 UTC，展示一律北京时间
- 日期：2026-10-23
- 状态：Accepted
- 背景：用户反馈「所有的时间都不是北京时间」。排查后确认是三处独立缺陷叠加，都不是存储问题——存储层一直是正确的「naive UTC」：
  1. **学习日时区默认值错了**。`app/days.py` 的 `STUDYFORGE_TIMEZONE` 默认 `"UTC"`，且全仓库没有任何地方设置它。于是学习日的 04:00 边界落在北京时间 12:00：上午学习被记到前一天，中午队列翻页，`today_key` / 打卡 / Deadline 倒数全部按 UTC 日算。
  2. **任务接口漏了时区标记**。`app/jobs/router.py::_out` 直接 `job.created_at.isoformat()`。SQLite 取回的时间戳是 naive UTC，序列化后成了 `2026-10-23T07:04:36`——浏览器把无偏移字符串当**本地时间**读，于是任务列表整体慢 8 小时。这是全仓库唯一一处绕过 `iso_utc()` 的时间序列化。
  3. **前端各写各的换算**。`lib/copy.ts::formatDay` 硬编码 `timeZone: "UTC"`，凌晨 0–8 点发生的事件显示成前一天；另有 9 处组件/页面直接 `toLocaleString()` 不带时区，服务端渲染用宿主时区、水合后用浏览器时区，两者不一致。
- 决策：
  - 存储不动。瞬时一律 naive UTC，与既有 `review.py` / `planning.py` 的约定保持一致。
  - `days.DEFAULT_TIMEZONE` 改为 `"Asia/Shanghai"`；`compose.yaml` 与两份 `.env.example` 显式写出 `STUDYFORGE_TIMEZONE=Asia/Shanghai`（容器里不靠猜）。环境变量仍可覆盖，测试用 `monkeypatch.setenv` 切换。
  - `_out` 改用 `app.attempts.iso_utc()`，输出 `+00:00`，与 `projects` / `knowledge` / `submissions` / `agent` 各 schema 的 `utc_timestamp` 序列化器口径一致。
  - 前端新增 `lib/copy.ts::APP_TIMEZONE = "Asia/Shanghai"` 与 `formatDateTime()` / `dayKeyOf()`，10 处调用点统一收口；`formatDay` 改用它。日键（`formatDayKey`、`lib/plan.ts` 的 `shiftDayKey`）**保持 UTC 固定**，因为 `YYYY-MM-DD` 是日历事实而非瞬时，跨时区换算反而会错一天。
- 理由：单一用户、本机运行、人在北京，UI 上的「今天」「04:00 学习日」「任务几点跑的」都必须是墙上时钟。把时区收敛成两个常量（后端 `days.DEFAULT_TIMEZONE`、前端 `APP_TIMEZONE`）比在 15 个调用点各写一遍 `timeZone:` 更不容易再次走偏。
- 影响与风险：历史数据不需要迁移——存的是 UTC 瞬时，只是过去按 UTC 日切分的学习日归属会与新口径不同（例如过去某天上午的打卡算在前一天）。这部分历史不重算，因为它记录的是当时的判定，重算会改写已发生的学习历史，违反「不删改学习历史」边界。测试：`tests/test_days.py::test_default_timezone_is_beijing` 断言默认时区与 04:00 边界，`tests/test_job_links.py::test_job_timestamps_carry_the_utc_offset` 断言接口带 `+00:00`，`frontend/tests/timezone-display.test.tsx` 用 UTC 与北京**日期不同**的瞬时锁住换算（中段时刻两种实现都能过，锁不住）。

## ADR-033 — AI 请求按「主题」幂等：作业行就是缓存
- 日期：2026-10-23
- 状态：Accepted
- 背景：用户连续两次报告同一个缺陷——「答案分析能反复触发」「检查一下是否还有 AI 任务是能刷新重试的，这是被杜绝的操作」。根因不是某一个按钮忘了 disabled，而是**服务端从来没有记住自己已经为同一个主题付过一次费**。前端按钮在作业结束时回到 idle，双击、开第二个标签页、刷新后重进页面，都会买到第二份相同答案。13 个 AI 入口里当时只有 2 个（知识点提取、图谱提取）有这层保护。
- 决策：
  - **一个守卫**：`jobs.service.find_live_job(session, type, ref_type, ref_id)`，只认 `pending`/`running`。命中即返回 `{"job_id": 已有的, "resumed": true}`，不新建行、不再调用模型。路由不再各写一套。
  - **身份字段写在 `progress` 里**：`create_job(..., progress={"stage": "queued", "attempt_id": ...})`。之所以不放独立列，是因为 `progress` 已经在入队那一刻落库，正好覆盖「create 到 worker 启动」这个双击窗口；worker 启动后 `update_progress` 是**整体替换**，因此必须把身份字段继续带上，否则守卫在作业开始后就失效——这是本实现唯一的隐性约束，已在 `create_job` 与调用点注释里写明。
  - **完成态的身份在 `result` 里**：`complete_job` 会 `progress=None`，所以「已完成」的查找必须读 `result`。只查 `progress` 的实现能通过双击测试，但永远查不到缓存，表现为「过一会儿再点又能生成」。
  - **答案分析以作业行为缓存，不写 `attempts`**：`attempts` 是 append-only（模型 docstring 明确 rows are never updated），而一次点评属于某次作答而非某道题，写进 `quiz_items.solution` 会让下一次作答看到上一次的点评。因此 `(item_id, attempt_id)` 的唯一记录就是那条作业行。
  - **粒度按产物定，不按入口定**：提示按 **(题, 级别)** 匹配，因为 level 1 与 level 2 是两份不同产物；变式题的 ref 从 `course` 改成 `quiz`/`item_id`，否则同课程任意两题共用一个守卫；课程生成没有 ref，全安装唯一。
  - **同步端点同样先查缓存**：`POST /quiz/{id}/answer-analysis` 是异步端点的旁路，不查就等于开了后门。
  - **客户端只做恢复，不做判定**：前端不猜「这是不是重复请求」，它只负责刷新后从 `/api/jobs` 找回仍在进行的作业并继续轮询（`useResumeJob`、`QuizSection` 挂载恢复）。判定权在服务端，否则前端一改就绕过去了。
- 理由：作业行本来就是「一次付费调用的记录」，让它兼任幂等键，比新增一张 `ai_requests` 表更小、也不会出现两处状态不一致。`find_live_job` 只有 6 行，13 个入口共用一个，新增入口时漏接是可以被 `tests/test_ai_dedupe.py` 直接指出的。
- 影响与风险：
  - 幂等窗口只在「进行中」与「已完成」两种状态。**失败**的作业不参与复用，重试是允许的（用户为失败付费了，不能连重试也堵死）。这一点是有意的：`find_live_job` 只看 `pending`/`running`。
  - 同一主题的两个请求若真正同时到达（未加锁的 read-then-write），仍可能各插一行；这与 `attempts` 的双击守卫同一个已知边界，不在本轮扩大范围。单人本机场景下窗口在毫秒级。
  - 测试：`tests/test_ai_dedupe.py` 8 项覆盖 13 个入口中的 8 类（解析、出题、课程生成、课时重生成、课程重生成、判分、提示分级、答案分析每作答一次、图谱触发不叠加，其中重生成一项覆盖两个入口）。该文件全部用「直接插入 pending 作业 + 手工完成作业」的方式构造，不依赖后台线程池——依赖线程池会让断言在并发批次里测到的是线程调度而不是守卫（本轮实际踩到：另一个文件遗留的真实 provider 作业占满两个线程，用例报「job never finished」）。


## ADR-034：单人密码门禁与固定 7 天会话（2026-10-24）

- 背景：用户明确要求使用 `.env` 既有 `ADMIN_PWD`，除首页外需要密码登录，并保护真实数据接口；随后明确不要 Docker 验证、停止后续测试并直接 Git 提交。
- 决策：保留单用户边界，后端统一鉴权，Next.js 在渲染前确认会话；浏览器走固定上游的同源转发。登录页复用首页真实动画组件，而不是复制动画代码。
- 会话：15 分钟签名 access + 7 天固定到期的随机 refresh；持久化会话支持重启，退出立即撤销；续期不延长 7 天。密码改动使旧 token 失效；空密码配置关闭业务访问。Cookie 为 HttpOnly/SameSite=Lax，HTTPS 使用 Secure；跨站写请求拒绝，登录有本地限流，认证响应及业务数据禁止缓存。
- 取舍：只新增独立会话表，不引入 JWT/账号库等依赖，不迁移学习历史。refresh token 保持稳定以适应并发 SSR/API 续期；单机限制见架构文档。

## ADR-035 — 单人私有服务器原生部署与一次性迁移（2026-10-24）

- 用户明确将部署范围从本机扩展到自己的私有服务器，继续单人密码访问；用户代码仍自行本地运行，服务器不执行上传代码，不增加注册或多用户能力。
- Next.js 与 FastAPI 由 systemd 运行，非 root、回环监听、单后端 worker。经用户确认复用现有 HTTPS 首页，既有模型网关路由与证书续期保持原配置；不新增本项目应用容器。
- 完整迁移一次本地一致快照及资料，核验内容哈希并保留回滚快照；上线后网站为写入来源，不采用 SQLite 文件双向同步，避免覆盖新学习记录。
- 数据与环境配置独立于版本目录；代码发布以版本目录和 `current` 链接切换。配置、维护及旧 FTS 索引限制见 `DEPLOYMENT.md`。
